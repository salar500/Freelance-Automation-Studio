# Testing book

Status: P4 proposed continuous testing standards; existing TEST definitions and outcomes preserved, all runtime tests NOT_RUN.

## Purpose
Owns test strategy, result semantics, risk coverage and evidence standards.

## Inputs and planned scope
Use phase-appropriate document reviews now; later unit, integration, system, offline, Windows compatibility, security, performance, recovery and installer checks. Prioritize original preservation, uncertain results and authorization boundaries.

## Records and working rules
Assign TEST IDs only to defined test cases. Record purpose, linked requirements/risks, prerequisites, input/expected result, environment, command/procedure, actual result and evidence. Outcomes: PASS, FAIL, EXPECTED_FAILURE (justified known defect), SKIPPED (reason), BLOCKED (prerequisite), NOT_RUN. Expected failure is not acceptance success. A zero-test run is not validation. Capture test counts where available and functional evidence otherwise.

## Acceptance criteria
Each gate has meaningful checks and trace coverage. Failures must be diagnosed as setup, product or specification issues; never remove assertions or hide failed/skipped tests. Gate-critical failures block approval; any noncritical exception needs documented human approval. P0 checks are in its milestone report; application tests are NOT_RUN because no application exists.

## P4 ownership and continuous verification
This book owns TST rules/strategy/results/gates, with detailed future scenario methods in [P4 verification specification](../specifications/P4-testing-verification.md). Master owns phase approval, P1/P2/P3 matrices own existing TEST definitions. No test tool adopted/installed and no executable test run during P4. All standards below are proposed for future authorized implementation, not compliance evidence.

TST-01 owner QA/component leads; scope every meaningful changed behavior; rationale catch defects early; enforcement changed REQ/components/consumers risk assessment selects unit -> contract -> integration -> targeted E2E then broader regression when warranted. Unit tests verify deterministic observable rules/transforms/state with fixed time/locale/seed, no real OS/network. Contract tests verify module input/output/config/error/IPC/schema negotiation/progress/cancel. Integration proves services/DB/files/supervisor/workers/artifacts/validators/reporting actual cooperation. E2E verifies create/configure/validate/execute/review/approve/export in P2 normal/failure flows. System/release proves installer/offline/packaged workers/migration/restore/Windows/security/resources/accessibility. Fakes supplement rather than replace OS/integration proof. No language-specific runner chosen until ADR and feasibility approval.

TST-02 owner traceability lead; scope important implementation/tests; rationale actual coverage; enforcement REQ/NFR -> P2/P3 design -> authorized source revision -> existing TEST -> fresh run/evidence -> acceptance. Before new TEST allocation inspect all three existing matrices (next available 0240, recheck at allocation); reuse equivalent case, register unique definition and owner. No new IDs allocated in P4. New/changed cases include ID, requirement, purpose/priority/owner, prerequisites, input/fixture version, steps or procedure, expected result, actual result/status, evidence and exact environment. Existing TEST definitions retain content/outcome; enhancements through authorized change with rationale/history. Obsolete cases retain retired ID/reason/replacement, no deletion/reuse. Deferred/unimplemented scope has explicit risk/owner/gate and NOT_RUN/BLOCKED, never implied tested. Requirement change triggers design/test impact and revalidation; stale evidence remains historical.

TST-03 owner QA/reviewer; scope test design; rationale independent business oracle; enforcement positive/negative/boundary/missing/invalid/unsupported/corrupt/cancel/timeout/crash/interruption/partial/integrity/unauthorized/approval-change/retry/export cases appropriate to risk. Verify counts/content/hash/observable effects with small hand-reviewed expected fixtures, independent parser/inspection where supported and metamorphic properties; do not clone production algorithm as oracle or assert only internal calls. Required fixture/profile scope and evidence named per test. Detailed four-module methods below preserve P3 conditional extensions; missing finalized capability profile blocks relevant test/implementation.

TST-04 owner fixture/QA lead; scope all committed/generated data; rationale confidentiality and reproducibility; enforcement synthetic or appropriately licensed fixture manifest with stable fixtureName/module/purpose/version/owner/license/seed/generator-spec/source hash/size/expected output/properties and malicious-content handling. Naming: module-scenario-vN; storage future tooling/fixtures/<module> for small reviewed inputs/manifests, large boundary fixtures generated into owned disposable run path. Generation script only later authorized/approved stack, versioned deterministic seed and size quota. Valid/invalid CSV/XLSX, digital/scanned-like/corrupt/encrypted PDF/DOCX, local pages/broken links/controlled logins, fault/recovery inputs contain no real client data or credentials. Never execute imported scripts; reviewed local web fixtures run only under explicit controlled-test exception/authorization. Cleanup removes owned eligible run files/processes, retains required failure evidence, no original/user-artifact deletion.

TST-05 owner test-run/resource lead; scope future runs; rationale constrained machine safety; enforcement read available CPU/memory/disk/process state, reserve storage, one heavy suite and one browser worker initially, adjust only measured safe profile. No conflicting browser profiles/ports/concurrent heavy jobs without documented justification; stale process detection uses runner ownership/session/creation token, not name/PID alone. Stop only verified owned stale process trees, preserve unrelated user processes. Reuse valid outputs/evidence for identical relevant inputs/implementation/environment; changed dependency/code/config invalidates affected proof. Resume by recorded test subset/new run with linkage, don't overwrite earlier failures; partial suite cannot become full pass. Full regression required P11 integration and P13 release, plus major shared/contract change risk.

TST-06 owner QA/evidence lead; scope each actual run; rationale truthful acceptance; enforcement runId, suite/test IDs/counts, passed/failed/expected-failure/skipped/blocked/not-run totals, exact OS/build/hardware/tools/modules/source/config/fixtures, commands/working directory/start/end/correlation, expected/actual, evidence hash/path, failure diagnostics and limitations. Categories mutually exclusive per test occurrence and reconcile planned/attempted counts. Capture runner exit status without masking pipeline failure; inspect actual nonzero test count and selected suite. For non-runner functional checks record direct observable evidence. Skipped/blocked are never passed. Fresh relevant passing evidence required after fixes; obsolete/stale runs historical. P3 report contract check PASSED/FAILED vocabulary is distinct from test-run PASS/FAIL and human approval.

## Formal quality gates
Each gate has a responsible reviewer, applicable mandatory checklist and measurable exit; missing mandatory evidence means BLOCKED. Future gates are NOT_RUN today. Noncritical exception follows master human approval with scope/expiry, never falsifies result.

| Gate | Entrance | Mandatory exit evidence | Owner |
| --- | --- | --- | --- |
| 1 Requirements | Authorized scope, existing catalog and owner decisions | No duplicate/conflicting active requirements; every in-scope item has acceptance/trace/disposition; unapproved affected requirement blocks implementation | Requirements owner |
| 2 Design | Verified prior baseline, proposed contracts and known risks | Applicable component/interface/security/recovery/UX consistency; unique IDs, valid links, open facts explicit; approved architecture/dependency tuple before adoption | Architecture/UX/security |
| 3 Implementation | Approved affected REQ/design/profile and executable task scope | Scoped review, formatting/static/type/boundary checks where applicable; all mandatory changed-unit/contract/security cases actually pass; no hidden skipped blocker | Code/QA reviewer |
| 4 Module acceptance | Implemented declared module capabilities and valid fixtures | Module integration/E2E normal/adverse/boundary/fidelity/count/original-integrity/cancel/recovery pass for supported profile, limitations disclosed | Module/QA owner |
| 5 System integration | Accepted modules and shared foundation | Cross-module orchestration/review/approval isolation, DB/artifact/backup/restart integrity, offline local flows; full scoped regression with trace | Integration QA |
| 6 Release | Approved scope, release candidate build and dossier | Real supported Windows + installer/upgrade/uninstall, license/dependency/security/offline/data/recovery/accessibility/performance mandatory evidence and human release approval | Release/owner |

## Local quality workflow and acceptance
Essential local checks use approved pinned available tools without hosted backend/AI/cloud login. Optional GitHub Actions may mirror local development checks only, never product runtime requirement. Pre-change baseline/impact -> developer selected tests -> explicitly authorized staged/pre-commit review -> PR consumers/security -> integration/full regression -> clean release/Windows/offline gates. Future tool/command record names working directory/runtime/options/resources/exit count/evidence; no executable scripts/CI during P4. Secret scanning, dependency/advisory/license checks supplement direct threat tests and do not prove an unknown binary license or OS compatibility.

Acceptance: test levels, all four module scenarios, offline/security/recovery/performance/accessibility, fixtures/resources, fresh result/trace rules and gate criteria are enforceable and owned. Existing 239 definitions NOT_RUN and pending implementation retained; no runtime or compliance claim. [P4 report](../milestone-reports/MS-0005-P4.md) records actual documentary checks.
